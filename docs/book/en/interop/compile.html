MoonBit++ Manual

Compiling to MoonBit

The compiler translates the type-checked program into MoonBit. moonpp build and moonpp run --compiled use it; “Compile to MoonBit” in the Playground shows the result directly.

Two translations are mixed: code expressible with MoonBit types becomes ordinary MoonBit code (the native translation), and the rest uses a dynamic uniform representation. Values are converted at the boundary between the two.

Native translation

Types that can be translated natively are native types, and the expressions that can be translated natively, using values of native types only, form the native fragment. A function whose parameters and result are native types, and whose body is in the native fragment, is translated into an ordinary (possibly generic) MoonBit function. The native types are:

  • Int, Double, Bool, Char, String, Unit;
  • Nat, as MoonBit’s BigInt (see Nat below);
  • type parameters and function types;
  • arrays Array[T] (with T native), as MoonBit arrays;
  • data types whose fields are all native types.

Indices and erased fields disappear, for example:

enum Vector[T] : Nat -> Type { Nil : …; Cons[n : Nat](T, Vector[T](n)) : … }
// compiles to
enum E_Vector[T0] { Nil; Cons(T0, E_Vector[T0]) }

Parameters that are not types (value parameters, like n of struct Scoped(n : Nat), and propositions) disappear like indices, so data types using them only in types or proof fields stay native. A data type with one constructor keeping one field (not of the type itself) after erasure becomes a MoonBit tuple struct, without an extra box:

type Ex Int                          // struct E_Ex(Int)
struct Scoped(n : Nat) {             // struct E_Scoped(E_Expr)
  e : Expr
  ok : closed(e, n) === true
}

#mbt types use their own names instead of E_… (see #mbt Types and Traits).

Instances of the Prelude’s #mbt traits (Show, Eq, Compare, Hash, Default, the operators, …) become MoonBit impls of the E_… types when native code needs them, derived instances included; Option and Result use MoonBit’s own impls, which print and compare as the Prelude’s instances do. So async functions (which only have native code) can print and compare these data too (and arrays and Map).

Arrays are not converted between native code and the uniform representation: as copies, they could not share their mutations. A function with arrays among its parameters or result has a native and a uniform version; native code passes arrays to native code, and uniform code to uniform code.

A global let of a native type whose definition is in the native fragment is native too: it is computed once, when first used, and native code refers to it directly, so the functions reading or writing it keep their native versions. Uniform code sees it converted; a global let holding arrays (or other parts that cannot be converted) is native only when no uniform code uses it, so that both sides see the same array.

struct Arena { kinds : Array[Int] }
let glob : Arena = { kinds: [1, 2, 3] }
fn kind_glob(e : Int) -> Int { glob.kinds[e] }   // fn f_kind_glob_t(e : Int) -> Int

A native function that cannot raise is a MoonBit function without raise (on the JS backend, a call of a raise function allocates and checks a result object). Only raise, calls of functions that may raise (function values and trait methods included) and calls through the uniform representation raise; runtime errors in native code (an index out of bounds, a division by zero, no matching arm) are not error values: they print the message of the uniform code and stop the program.

Uniform code can only call the uniform version of a function with arrays (or other parts that cannot be converted) among its parameters or result. So the entry should stay in the native fragment: main (like global lets) is native when its definition is in the native fragment, and may use return; when main can only be uniform, the functions of that kind that it calls run in the uniform representation too.

moonpp build --verbose lists the functions and global lets of the program (main included) without a native version, with the reason, followed through types and fields to its source, for example:

without a native version (they run in the uniform representation):
  bump: its body is not in the native fragment: in `glob`, the global let glob is not native
  glob: it holds arrays, and code in the uniform representation uses it
  sum_n: its signature has no native translation

Nat

When type checking, Nat is the unary Z, S(n), and proofs compute with the definitions. At run time (in the interpreter and in compiled programs), a Nat is an arbitrary-precision integer, MoonBit’s BigInt:

  • Z is 0 and S(e) is e + 1; numerals are BigInt literals (such as 10N).
  • A pattern S(…S(p)) (k levels) tests whether the value is ≥ k (= k when p is Z), and each level binds the value minus its depth.
  • The Prelude’s +, *, ==, compare, to_int, to_string on Nat and int_to_nat are BigInt operations.

So arithmetic on Nat no longer takes time proportional to the numbers, and does not overflow the stack by deep recursion:

fn fact(n : Nat) -> Nat {
  match n {
    Z => 1
    S(k) => n * fact(k)
  }
}
// native translation
fn f45_fact_t(n : BigInt) -> BigInt raise {
  match n {
    n0 if n0 == 0N => 1N
    n1 if n1 >= 1N => n * f45_fact_t(n1 - 1N)
    _ => rt_fail("no match")
  }
}

fact(30) is 265252859812191058636308480000000. Functions you define by structural recursion (another addition, say) still recurse once per level, each level being a BigInt operation. Nat is not a MoonBit type: the parameters and results of a #mbt fn cannot be Nat, since a BigInt from MoonBit could be negative.

Types shaped like Nat

In compiled code, data types that have the shape of Nat after erasure are BigInts as well: two constructors, one without kept fields (the zero), and one keeping a single field whose type is the data type itself (the successor). The most common one is the finite set Fin:

enum Fin : (Nat) -> Type {
  FZ[n : Nat] : Fin(S(n))
  FS[n : Nat](Fin(n)) : Fin(S(n))
}

The implicit fields n of FZ and FS are only used in types and are erased, so a value of Fin(n) is just an index: FS(FS(FZ)) is 2N. Getting an element of a vector by a Fin therefore compiles to a recursion on an integer index:

fn[T0] f46_vector_get_t(self : E_Vector[T0], i : BigInt) -> T0 raise {
  match (self, i) {
    (E_Vector::Cons(x, _), n0) if n0 == 0N => x
    (E_Vector::Cons(_, xs), n1) if n1 >= 1N => f46_vector_get_t(xs, n1 - 1N)
    _ => rt_fail("no match")
  }
}
  • A type of your own like enum Peano { Zero; Succ(Peano) } is compiled the same way.
  • When an implicit field is used at run time (a pattern FS[m](_) => m.to_int(), say), it is not erased, and the type stays an ordinary enum.
  • Propositions, error types, #mbt types and imported types keep their representations.
  • Instances for such types (other than Nat) do not become MoonBit impls, since they are all BigInt in MoonBit; code using those instances uses the uniform representation.
  • The interpreter does this for Nat only (it does not erase).

Uniform representation

Everything else (type-level computation, GADT refinement, non-#mbt traits, etc.) uses the uniform representation Value. It is an extensible enum (MoonBit’s extenum) in the runtime, with fixed variants VInt, VFun, and so on; each generated file uses extenum Value += { … } to add the constructors of its own data types. Indices and erased fields do not appear, and fields are Value. For example, the GADT in examples/basic.mbtpp of the repository (the Exp of enum and indexed types):

enum Exp : [T] -> Type {
  IntLit(Int) : Exp[Int]
  Add(Exp[Int], Exp[Int]) : Exp[Int]
  If[T](Exp[Bool], Exp[T], Exp[T]) : Exp[T]
  …
}

compiles in basic.mbt to

extenum Value += {
  K_Exp_IntLit(Value)
  K_Exp_Add(Value, Value)
  K_Exp_If(Value, Value, Value)
  …
}

The match in eval is native:

fn f19_exp_eval(self : Value) -> Value raise {
  match self {
    K_Exp_IntLit(n) => n
    K_Exp_Add(lhs, rhs) => VInt(as_int(f19_exp_eval(lhs)) + as_int(f19_exp_eval(rhs)))
    …
  }
}

The result type of eval varies with the index (the IntLit branch returns Int, the BoolLit branch returns Bool), which MoonBit’s type system cannot express, so its result is still Value. Runtime support (apply, primitives, the dynamic pattern matcher) lives in the generated mbtpp_runtime.mbt; it gets constructor names and fields (for display and equality) from decoders that each file registers in fn init. The two kinds of code convert values at their boundary.

Because Value can be extended from other files and other packages, this representation also suits separate compilation of multiple MoonBit++ packages in the future.

Erasure

  • Type parameters are always erased.
  • Other implicit parameters and implicit constructor fields are erased when they are used only in types; an implicit parameter used at run time is an ordinary parameter of the native function.
  • Proofs are always erased: parameters and fields whose type is a proposition (implicit or not), lets of proofs and calls of lemmas produce no code, and lemmas themselves are not generated; a match on a proof runs its first arm (a match on a proof of an empty proposition becomes an abort). So a #mbt fn can have proof parameters, like fn get(xs : Array[Int], i : Int, p : i < n), and the exported MoonBit function does not have them.

Performance

A fib program runs about 40 times faster when compiled (7.85 s interpreted, 0.18 s compiled). Before constructors became native variants of Value, data in the uniform representation was VCon(constructor name, field array) and matching compared strings; with native variants, evaluating an Exp tree with 2^18 leaves 20 times dropped from 2.65 s to 1.26 s.

Values are converted recursively, by value, between native code and the uniform representation (expr_to_value, expr_of_value). For highly shared data (a DAG, like expressions sharing subterms), the conversion unfolds the sharing, and its size can grow exponentially. Functions on such data should stay in the native fragment, so that the data does not cross the boundary: for example, keep them away from code that needs the uniform representation (type-level computation, GADT refinement).
